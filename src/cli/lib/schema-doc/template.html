Allowealth Data Model

How the household finance app stores its money, its members and its logins. One SQLite-dialect schema, defined with Drizzle, runs on local SQLite during development and on Cloudflare D1 in production.

Rules every table follows

Scoped to a workspace

A workspace is one household's books. Financial rows carry workspace_id with ON DELETE CASCADE, and every service query filters on it.

Money is text

amount, balance and budget_amount are decimal strings, never floats. Every money row stores its own currency.

Who did it

created_by_user_id on every financial row. Transactions also record who last edited and who deleted them.

Soft deletes

transactions, accounts and users set deleted_at instead of losing history. Closed accounts keep status = closed.

Text ids

Primary keys are text ids generated in the app (nanoid). There are no autoincrement keys.

Integer timestamps

Dates are integers mapped to Date by Drizzle. Recurring dates (start_date, due_date) are ISO text instead.

The financial core

Eleven tables hold the household's money. Arrows point from the row that holds a foreign key to the table it references, so each arrow reads as "many of these belong to one of those".

Budgeting

budget_categories are the labels for spending and income. They are not the same as account categories. A budgets row sets one category's limit for one month in one currency. The unique key is (workspace, category, month, year, currency). is_closed locks a month after the books are closed.

Ledger

Each row in transactions is one expense, income or transfer. account_id is always the source. A transfer also sets to_account_id and leaves category_id empty. Six of its 14 indexes start with workspace_id and end with transaction_date, to serve monthly reports.

Recurring

A recurring_templates row describes a bill, salary or installment plan. Active templates generate recurring_occurrences, one per due date. The unique key (template_id, occurrence_number) makes it safe to run generation more than once. Confirming an occurrence creates exactly one transaction and links it back through the unique transaction_id.

Accounts & net worth

accounts are bank accounts, wallets, investments and debts. account_class sorts them into liquid, non-liquid and debt. Each balance change appends a row to account_history. A month-end account_snapshots row copies every account's balance into account_snapshot_items, so later edits never rewrite the past.

Two separate records of money

This is the part of the model most likely to surprise a new contributor. Transactions record what happened. Account balances record what the household has. Writing a transaction does not change any balance.

The design matches how the household actually works. Balances are read off a bank app and entered by hand, often for a past month-end. Transactions are logged for budgeting. Keeping the two separate means a missing receipt never makes a balance wrong. The cost is that the two can disagree, and nothing in the schema reconciles them.

Identity and workspaces

Login is handled by Better Auth, which owns its own tables and column naming (camelCase). The app keeps a separate users table for workspace membership and roles. The two are joined by sharing the same id.

Better Auth tables

user, session, account (password and Google credentials), verification, twoFactor and passkey follow Better Auth's expected shape. Change them only together with a Better Auth upgrade.

MCP OAuth provider

oauthApplication, oauthAccessToken and oauthConsent come from Better Auth's MCP plugin. They let AI clients connect to the MCP server. Their userId and clientId columns have no foreign-key constraint.

Membership

A user belongs to at most one workspace, with role admin or member. super_admin is a system role. Invitations carry a single-use token and an expiry. user_meta and workspace_meta are key-value stores for preferences, with keys checked against an allowlist in the service layer.

Audit

audit_logs records each action with old and new values as JSON, keyed by entity_type and entity_id. It is the only table whose created_at uses Drizzle's millisecond timestamp mode.

Before you change it

  • Timestamp defaults are in milliseconds, reads are in seconds

    The SQL default sqliteTimestampNow writes milliseconds. Columns declared integer(…, { mode: 'timestamp' }) are read by Drizzle as seconds. A row that relies on the default reads back as the year 58727. Services pass created_at and updated_at explicitly, which hides this. Set them explicitly in new code, or fix the default and its migration.

  • Users are removed by soft delete for a reason

    Every created_by_user_id references users.id without an ON DELETE action. Hard-deleting a member who created records will fail the foreign-key check. Use deleted_at.

  • Two kinds of category

    The Drizzle export categories maps to the SQL table budget_categories, for spending and income. account_categories groups accounts on the net-worth page. They are unrelated.

  • Some references are not enforced

    workspace_invitations.invited_by_user_id, the OAuth provider tables' userId, and the user ↔ users join have no FK. Clean them up in the service layer when deleting.

  • Legacy tables are still in the schema

    sessions, password_reset_tokens, email_verification_tokens, oauth_accounts, user_mfa and user_mfa_backup_codes predate Better Auth. Don't build on them. user_mfa and its backup codes are no longer exported from the schema index.

  • ADR 004 lists an api_keys table

    No such table exists in the schema. The ADR is out of date on this point.
